# PR Review 导读

让维护者理解一份 PR 解决什么问题、代码如何工作，以及按什么顺序读代码才能判断改动是否合理。调用示例：`$pr-review-guide https://github.com/owner/repo/pull/123`。

## 确认实际评审对象

- 核对 PR 当前状态、head SHA、base 分支与 SHA。已合入时说明合入目标。读取实际 diff，不把标题、描述、历史聊天或旧 review 结论当作当前实现。
- 对叠加 PR 区分本 PR 增量与前置实现。只追踪影响理解的前置依赖，说明本 PR 在整个功能中的位置，不把其他 PR 的能力算作本 PR 新增。
- 优先使用可用的代码托管连接器读取 PR 和源码，再考虑 CLI 或网页。本地仓库用 Git 读取，必要时 fetch 对应远端引用。不为导读切换用户现有分支、改写提交或清理 worktree。
- 对齐源码与评审 head。无法获取某部分内容时明确缺口，继续解释已核实部分，不假装已读完整代码。

## 沿行为理解实现

先读变更清单，找出接口、入口、主流程及测试，再按需要阅读被调用的已有实现与调用方。阅读范围应足以解释关键行为，不机械遍历全仓。

围绕一个真实输入或用户场景组织理解：

1. **问题与结果**：什么条件触发旧问题，修改后行为如何改变。只在证据支持时给出具体前后对比。
2. **职责与边界**：哪些包或模块负责调度、渲染、数据、传输或生命周期。区分新增能力、复用能力和后续 PR 才接入的能力。
3. **执行过程**：从入口沿同一案例追踪调用、数据和状态，直到完成。涉及初始化、异步等待、错误、取消、恢复、更新或卸载时，解释本 PR 实际改变的路径。
4. **关键理由**：解释为什么在这个位置增加接口、包装层、标记或等待，而不是只复述函数名。大段 diff 先区分实质逻辑与移动、缩进或格式变化。
5. **验证证据**：测试是否检查了预期行为，哪些断言能判断实现成立，哪些边界尚无证据。存在测试不等于已执行，最终页面出现内容也不自动证明 SSR、水合或状态复用成功。

区分代码已确认的行为、作者描述、推断和待验证假设。发现有证据支持的问题，直接说明触发条件、后果与位置。不为了给出审查意见而猜测缺陷，也不把阅读导读写成“已完成全面审查”或“保证没有问题”。

## 设计阅读顺序

按理解依赖排列文件，不照 GitHub 文件排序逐项摘要。常见起点是接口或模型，再到入口和核心流程，随后看数据与生命周期，最后用测试核对承诺。小 PR 可以直接从唯一的核心改动开始。

每个推荐阅读点写清：

- **看哪里**：具体文件和关键符号，附可点击的代码位置。
- **它负责什么**：在整体流程中的作用，以及本 PR 改变了什么。
- **重点判断什么**：提出与改动直接相关、可以通过代码或测试回答的问题，例如先后顺序、状态所有权、失败传播或兼容行为。不要只写“注意正确性和性能”。
- **接下来连着看哪里**：需要对照的调用方、另一端实现或测试及其原因。

优先给出 `blob/<head-sha>/<path>#L<line>` 形式的永久链接，引用删除前实现时使用 base SHA。行号必须来自已读取的文件，避免链接到整个目录或无定位的 PR 首页来代替关键证据。本地文件使用绝对路径链接。先前 SHA 的导读在 PR 更新后应重新核对。

## 输出给用户

默认沿用用户语言，篇幅随复杂度调整。先让用户知道现在应打开哪个文件，不把元数据和背景调查放在主体前面。

通常包含：

- 开头用一小段说明 PR 的目的、实际效果和它在整体功能中的位置。状态或基线差异影响理解时就近说明。
- 用一个最小场景说明为什么需要改，必要时用简短流程图、调用链或对照表帮助理解。图中的函数、步骤和顺序必须能对应实际代码。
- 按推荐顺序给出阅读点，解释用途、设计理由和具体检查重点。把接口定义与执行位置、服务端与浏览器端等相关文件连起来讲。
- 将关键承诺映射到相应测试，说明普通路径与受影响边界该如何验证。没有运行测试时如实说未运行，引用 CI 或既有日志时写明对应 head 和实际覆盖范围。
- 对影响 review 的已知限制或证据缺口就近说明，建议首先打开的文件或函数应明确可见。

不固定章节数量，不堆满文件清单或通用检查表。术语首次出现时结合当前案例解释。短代码只展示帮助理解的真实逻辑，伪代码需要标注，不虚构 API、性能收益或测试结论。

这项调用本身只授权读取与解释。不要自动发表评论、批准、合入、修改源码或执行发布。需要运行测试时根据导读中真实的不确定性选择定向检查，不为说明一份 PR 默认启动全套昂贵构建和浏览器测试。用户另外要求完整 review 或修复时，按其明确范围继续。
