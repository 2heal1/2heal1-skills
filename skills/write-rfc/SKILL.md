# 技术 RFC 写作

让读者能够判断问题是否成立、方案如何工作、接受哪些代价，以及如何验证与落地。

## 1. 任务与证据

从用户材料和项目中确定评审读者、范围、约束、待决策事项及交付位置。沿用用户语言和目标平台。本地默认交付可编辑的 Markdown，HTML 只作可选预览。写作不自动授权发布、群发或变更业务系统。

优先读取代码、接口、测试、日志和已有决策，外部引用查阅原始材料。影响核心设计的缺失信息明确列为待确认，同时完成可确定的部分。不要因次要信息缺失停写。

对重要主张区分以下状态，无需每句话加标签。不编造基线、收益、测试结果、负责人或时间承诺。

| 状态 | 所需说明 |
| --- | --- |
| 已观察事实 | 条件、结果与来源。测量还需版本、环境、方法和单位。 |
| 假设或估算 | 依据、适用条件、不确定性和验证方法。 |
| 验收目标 | 期望达到的标准。未确认的阈值标为建议值。 |
| 推荐决策 | 选择理由、接受的代价和可能推翻结论的条件。 |

本方案已落地的代码称为“当前实现”或直接使用组件名称，不称为“参考实现”。社区项目用其名称，写清与本方案的借鉴或对比关系。

## 2. 阅读顺序

新 RFC 读取并裁剪 [RFC 模板](assets/rfc-template.md)。改写时保留有效内容，按读者理解方案的顺序合并、移动或替换旧段落，删除过期结论。不要为了保留旧结构而不断追加补充章节，也不机械生成模板中的所有章节或空表格。

- **摘要：** 问题、核心做法和预期效果，以及直接影响采用的关键条件。评审状态放属性栏，集成进展、验证缺口和开发待办放实现情况。
- **背景与选择依据：** 先交代场景和参与方，再说明现状、问题、目标与约束。问题描述允许不同解法。用于解释“为什么需要本方案”的社区实践和现有实现应放在详细设计前。
- **技术实现：** 用明确的“技术实现”或“技术设计”章节承载核心机制。沿同一个案例讲清请求由谁发起、经过哪些组件、数据如何传递，以及何时完成或失败。多条执行路径分别说明差异，共用处理集中讲清，并指出各路径在哪里调用它。先用最小示例帮助理解行为，再展开机制和完整接入配置，不能用配置说明代替设计。
- **取舍与落地：** 按同一组条件比较可行备选与维持现状，给出选择理由、代价和未解决冲突。按项目需要补充验证、兼容、迁移、发布、观测与回退。未知项区分决策前必须解决、实现中验证和明确延期。

关键限制、反例和影响方案成立的未知项放在对应设计旁。同一缺口只详细说明一次，跨章节汇总用链接定位。完整 API 清单、长日志和推导可放附录。章节衔接不明显时，用普通正文点明本节主要主题与前文的关系，不复述流程，也不只解释第一个小节。引用块用于实际引用原文。

### 标题命名

文档标题点明方案对象与核心改动。章节标题用简短、明确的技术主题或动宾结构，同层级保持相近粒度。避免疑问、叙事和评价性对比句，例如将“数据如何生成、部署和更新”改为“部署数据管理”。保留必要的对象与限定，不为缩短而使用“处理”“其他”等空泛名称，不设字数限制。

### 社区实践与方案取舍

社区实践先解释解决的问题和实现方式，再判断本方案能否复用。优先采用“方案｜解决的问题｜实现方式｜本文可以复用什么｜还需要解决什么”五列，按任务裁剪。区分直接采用、改造接入和借鉴设计，不把示例未覆盖写成项目不支持。只证明局部能力的 API、测试或演示放在所支撑的技术判断旁，不作为完整方案并列。

社区调研表与本方案的备选决策表承担不同问题。前者判断已有能力如何复用，后者说明为什么选择某条设计路径，不必为同一判断重复建表。需要借鉴写法时，按问题读取 [社区范例](references/community-patterns.md)。

## 3. 关联 RFC

先读取相关文档并确定内容归属，完成后联合检查受影响的 RFC。

- **职责：** 每项机制、接入方式或运行策略的详细说明由一篇负责。公共机制、具体接入与部署差异分别归位，不把后续方案的工作混入基础方案。
- **引用：** 其他篇保留理解本篇所需的场景、使用方式和新增条件，就近链接到负责细节的实际章节，不重复维护完整原理、示例或配置表，也不写成只有链接的索引。
- **一致性：** 对照证据核对术语、API、参数归属、默认值、单位、版本和资源地址，以及正常、缓存、失效、失败、取消、水合等相关行为及其实现状态。不同层级或版本的差异应说明原因，不强行统一。
- **链接维护：** 内容迁移后检查标题、章节号和目标。发布到文档平台时，将本地交叉引用转换为可访问的文档链接，能定位到章节时直接定位。

只修正任务范围内的文档。范围外的问题说明影响和建议，不因联合检查扩大修改或发布范围。

## 4. 表达与材料

- 面向不了解内部背景的读者，先说明对象及其行为，再引入项目名、缩写和内部角色。案例先交代参与方，必要时用分区图定位。“契约”等抽象词只有含义明确且确有必要时才使用。
- 正文写清谁在什么条件下做什么、为什么及其结果，默认不用分号串联独立判断。将“显著提升”“无缝”等评价改为机制、条件、成本或验证方法，保留对用户设想的客观判断。
- 每段提供新信息。删除套话、重复总结、给作者或维护者看的提示，以及无助于评审的自我说明。保留证据、原因、边界与未决项，不以字数或章节越少越好为目标。
- 连续文字承载多项规则、状态或关系时，用图、表或代码替换适合的部分，并删除已被覆盖的文字。不把长段原样搬进表格或代码注释，也不为展示代码虚构尚未定义的 API。
- 来源放在所支撑的判断旁，文末不重复罗列已介绍的方案或链接。删除参考列表时保留仍在使用的链接定义。图源、生成脚本和编辑路径作为交付资源保存，默认不出现在正文、图注或附录。

涉及多方协作、状态变化或需要改写密集文字时，读取 [视觉与动态演示指南](references/visual-guide.md)，按信息选择并实际制作。简单内容可以保留短段落，不设字数触发线、最低图数或图文比例。

## 5. 复核与交付

完成后检查以下结果，发现问题直接修改：

1. **可评审：** 关键判断有依据，推荐有代价，未知项没有被写成已实现事实。评审任务先报告影响决策的证据缺口、矛盾与遗漏。
2. **可追踪：** 读者能从目录找到技术实现，沿具体输入理解数据、步骤和结束条件。完整配置已有机制说明作为前提，关联 RFC 按第 3 节联合核对。
3. **无重复与错位：** 复核完整目录及正文、图表、代码、图注和附录，检查内容归属、前后条件和密集文字。修正全文同类问题，不只改用户指出的句子。
4. **交付一致：** 按视觉指南检查实际渲染。格式转换或发布后回读成稿，核对顺序、代码、表格、图片与引用，确认没有丢失内容或残留被替换的原文。

交付文档入口、必要的可编辑材料、仍待决策的问题和实际验证情况。没有生成或无法验证的内容如实说明，成稿不留指导性占位符。不要因章节不齐或没有 GIF 就判定 RFC 不合格。
