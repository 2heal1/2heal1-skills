# 技术 RFC 写作

交付可评审、可实施、可验证的技术提案。读者应能据此判断：问题是否成立、推荐方案为何成立、接受哪些代价、如何验证与落地。

## 写作原则

- **面向不了解内部背景的读者。** 先说明对象及其行为，再引入项目名、缩写和内部角色名；案例先交代场景和参与方，必要时用分区图定位。优先使用具体名称；“契约”等抽象词只有在含义清楚且确有必要时使用。
- **精简表达，保留必要信息。** 删除套话、重复背景、空泛形容词和图文复述，保留约束、机制、边界、失败路径、兼容性和验证条件。每句话应增加信息，不反复总结目标或机制。成稿只保留帮助读者理解和评审方案的内容，删除写给作者或维护者的提示，以及无助于判断的自我说明。不以字数少、章节少或固定页数为目标。
- **用完整句子写清动作与因果。** 默认不用分号串联正文中的独立判断。写清谁在什么条件下做什么，以及带来什么结果。解释代价时指出额外工作和消耗的资源，解释限制时指出触发条件与可观察后果，避免只罗列抽象名词。改写时补足逻辑关系，不只替换标点。
- **用证据支撑判断。** 区分已观察事实、假设、估算、目标与推荐。关键结论旁给出可追溯来源或推导，不在文末重复堆放正文已经说明的方案和链接；删除参考列表时保留正文仍使用的链接定义。没有数据时说明未知和验证方法，不编造基线、收益、测试结果、负责人或时间承诺。
- **明确推荐及其代价。** 可以提出主张，也应指出用户设想与证据的冲突。把“更优雅、显著提升、无缝、易扩展”等评价改为具体行为、适用条件和成本；不要把主观偏好伪装成共识。
- **用同一个案例贯穿。** 从现状的问题输入，走到方案行为、异常分支和验收；比较前后或不同方案时使用相同条件。
- **视觉承担信息。** 主动为跨组件关系、执行顺序、状态变化、数据差异选择图示；图中呈现文字难以直观看到的关系。简单到一句话即可说明的改动无需配图，不设最低图数或图文比例。

## 工作方式

### 1. 明确任务与证据

从用户材料和现有项目中确定：待决策事项、评审读者、范围、约束、交付位置及已有模板。沿用用户语言和目标文档平台；本地默认交付可编辑的 Markdown，HTML 仅作可选预览，不能替代正文源文件。遵循用户要求的保存或对话交付方式，写作本身不授权发布、群发或变更业务系统。

优先读取相关代码、接口、测试、日志、数据和已有决策；外部引用查阅原始文档。将会改变核心方案的缺失信息列为待确认，同时完成能够确定的部分。仅当答案实质影响设计时提问，不因缺少次要信息停写。

明确区分本方案自身实现与社区方案。本方案已落地的代码称为“当前实现”“本方案的实现”，或直接使用组件名称，不称为“参考实现”。介绍社区方案时写明项目名称及其与本方案的借鉴或对比关系。

对重要主张区分其状态，不要求每句话加标签：

| 状态 | 写法 |
| --- | --- |
| 已观察事实 | 描述条件、结果和来源；测量还需版本、环境、方法与单位。 |
| 假设或估算 | 说明依据、适用条件、主要不确定性和验证方式。 |
| 验收目标 | 明确是期望达到的标准；未获确认的阈值标为建议值。 |
| 推荐决策 | 写出选择标准、理由、接受的缺点及可能推翻结论的条件。 |

### 2. 组织论证

起草新 RFC 时读取并裁剪 [RFC 模板](assets/rfc-template.md)。每轮修改都重审全文的论证与阅读顺序：新增信息放在读者需要它的位置，同时合并重复、删除过期结论和无用内容，不能只向文末追加章节。保留有效结构，不机械生成所有章节、空表格或大量“无／不适用”。

摘要聚焦问题、核心做法和预期效果，可保留影响采用的关键代价或使用条件。文档评审状态放属性栏，已有集成、完成程度、验证缺口和开发待办放实现情况或后续计划。通常不把这些进展混入摘要，只有直接决定方案成立或适用范围的信息才在摘要中简述。

正文应让读者找到以下内容，可合并或按需展开：

- 决策摘要与问题证据；问题描述应允许其他人提出不同解法。
- 目标、非目标、约束和一个具体的使用前后对照。
- 选择依据：已有方案、当前实现及其证据若用于回答“为什么需要这个设计”，应在详细设计前交代；不必为了模板单列章节。
- 方案概览，以及支持实现的接口、数据流、规则和异常行为。
- 关键取舍：可行备选方案与维持现状，按相同标准比较；记录选择依据和未解决的冲突。
- 验证计划；涉及现有使用者或运行系统时，补齐兼容、迁移、发布、观测和回退。
- 开放问题：区分决策前必须解决、实现中验证和明确延期；重大未知项不要藏进附录。

先解释使用者看到的行为，再展开实现规则，并使规则与前文示例对应。完整 API 清单、长日志和细节推导可放附录，关键限制和反例留在正文。需要借鉴写法时按问题读取 [社区范例](references/community-patterns.md)，无需每次通读外部 RFC。

从整体方案或执行过程转入实现细节时，如关联不明显，用简短的普通正文说明本节承接前文的哪些内容。衔接应覆盖本节主要主题，不只解释第一个小节。只点明联系，不复述已有步骤，也不机械地为每节添加导语。章节过渡不使用引用块，引用块用于实际引用原文。

#### 关联 RFC 的职责、去重与一致性

编写、修改或评审关联 RFC 时，先读取相关文档，确定各篇负责的问题、决策和设计细节。完成后把受影响的 RFC 放在一起复核，不只检查当前一篇。

- **明确内容归属。** 同一机制、接入方式或运行策略的详细说明只由一份 RFC 负责。公共机制与具体接入、部署的差异分别放在对应文档，不将后续方案的工作混入基础方案。
- **去重但保留阅读上下文。** 其他 RFC 简述本篇如何使用该能力、有哪些新增条件，并就近引用负责详细说明的章节。避免重复维护原理、配置表、完整示例和验证清单，也不要为去重删除理解本篇所必需的场景、关键限制或取舍，把正文变成链接索引。
- **核对配置与行为。** 对照代码和证据检查术语、实例名称、API、参数归属、默认值与单位、版本和资源地址。按涉及的功能核对正常流程、缓存命中与未命中、失效、超时、失败回退、取消和水合等行为，以及实现状态与验证范围。不同层级、版本或适用条件造成的差异应说明关系，不为文字一致而强行统一。
- **维护交叉引用。** 链接指向实际负责该内容的文档和章节。内容迁移或章节调整后，更新受影响的引用，检查标题、章节号和链接目标。发布到文档平台时，将本地引用转换为可访问的文档链接，能定位到对应章节时直接定位。

在本次任务范围内修正受影响的文档。范围外的一致性问题说明影响和建议，不因联合检查自动扩大修改或发布范围。

### 3. 制作有用的视觉材料

涉及多方协作、并发、生命周期或体验变化时，读取 [视觉与动态演示指南](references/visual-guide.md)，选择并实际制作能降低理解成本的图或演示，不只留下“此处放图”。

- 关系、边界、顺序与状态优先使用可维护的 Mermaid 或矢量图；数据使用可复现的绘图工具；实际界面使用真实截图或录屏。
- 图、正文、代码中的术语和条件保持一致。图注只补充帮助理解的结论或必要条件，读图即可理解时无需另加说明。仅在容易误认成实测或已实现行为时区分示意与实测，不机械添加“非性能测量”等声明。正文解释图中无法充分表达的原因和例外。
- GIF／视频用于时间、动作或交互本身构成论据的情况。有误认风险时区分真实录制、原型演示和概念动画，并保留静态图或文字回退。
- 根据当前可用工具制作；不要求安装特定付费服务。不具备录制或渲染条件时，交付可读的静态表达或明确标注的分镜／演示步骤，说明未完成项，不伪称已生成或已验证。

### 4. 编辑与验证

完成后按决策需要检查，发现问题直接修订：

1. **论证：** 关键判断是否有证据或明确假设？是否公平比较可行替代方案？已拒绝的方案与延期研究是否分开？
2. **完整性：** 涉及的边界、失败、兼容、成本和验收是否足以评审？核心未知项是否显露？
3. **表达与顺序：** 每段是否提供新信息，且不依赖读者掌握内部背景？检查摘要、正文、图注与附录之间的重复、维护提示和无关说明，以及前提是否晚于结论出现。修改应覆盖全文同类问题，保留影响判断的证据、兼容范围和验证限制，不用术语堆叠代替论证。
4. **视觉：** 实际渲染检查图的方向、标签、布局和可读性；播放已生成的动态媒体，核对顺序、字幕与真实条件。不能预览时明确说明限制。
5. **交付：** 关联 RFC 先完成第 2 节的一致性复核。检查引用、相对路径和媒体链接，保留可编辑源文件及需要的静态回退。正文、图注及附录默认不展示图源链接、生成脚本或编辑维护路径，也不把删掉的维护提示自动移到附录。读者需要的证据引用仍保留。成稿中不留指导性占位符，尚未确定的设计内容应变成明确的开放问题。

评审任务先报告影响决策的证据缺口、矛盾和遗漏，再给具体修改；不要因为章节不齐或没有 GIF 就判定不合格。交付时提供文档与媒体入口、仍待决策的问题和实际验证情况。
